# Инструменты prod-варианта простым языком

Это краткая памятка по инструментам промышленного варианта проекта, где MAX-бот используется как входной канал, жизненным циклом пакета управляет оркестратор, а данные документов после приёма не покидают контур компании.

| Инструмент | Для чего нужен | Простое объяснение для бизнеса |
|---|---|---|
| MAX-бот | Принимает фото и команды от сотрудников. | Это удобная входная точка для пользователя. Через бота сотрудник просто отправляет документы, не думая о внутренней обработке. |
| MAX API | Передаёт сообщения и файлы между MAX и системой. | Это канал связи между ботом и сервисом. Он нужен, чтобы система могла получить фото и отправить сотруднику ответ. В MAX не возвращается содержимое документа. |
| Intake service / Bot API | Принимает пакет в систему и запускает процесс обработки. | Это входной шлюз проекта. Он фиксирует пакет, сохраняет данные и передаёт его дальше в управляемый процесс. |
| Orchestrator | Управляет всем жизненным циклом пакета. | Это диспетчер процесса. Он понимает, на каком шаге находится пакет, что делать дальше, когда повторить шаг и когда перевести пакет в ошибку. |
| Workflow состояния | Показывают, где находится пакет: `queued`, `processing`, `ready`, `manual_review`, `imported`, `error`. | Это понятная карта пути документа. По статусу можно быстро понять, пакет уже готов, требует проверки или завершился ошибкой. |
| PostgreSQL | Хранит пакеты, статусы, результаты и историю обработки. | Это главный реестр проекта. Именно здесь лежит вся деловая информация, с которой работает 1С. |
| Локальное или объектное хранилище | Хранит исходные фотографии и файлы пакета. | Это архив фотографий и вложений. Он нужен для хранения исходников, но не является главным местом, откуда 1С собирает документ. |
| OCR Worker | Выполняет фоновую обработку пакета. | Это рабочий механизм, который не мешает пользователю ждать в чате. Он берёт пакет и передаёт его на распознавание внутри контура компании. |
| On-prem OCR | Считывает текст и таблицы с фотографий внутри контура компании. | Этот инструмент "читает" документ с изображения без отправки фото во внешние облака. Он превращает фотографию в текст, пригодный для дальнейшей обработки. |
| On-prem LLM | Приводит распознанный текст к структуре, понятной бизнесу. | Он превращает сырой OCR-текст в данные: номер документа, дату, поставщика, строки товаров и суммы. Содержимое документа при этом не уходит во внешние API. |
| Validation rules | Проверяют, достаточно ли качественно распознан документ. | Это бизнес-проверки качества. Они помогают не пропускать в 1С заведомо плохие или неполные документы. |
| Manual review | Отдельный сценарий для спорных документов. | Если документ распознан неуверенно, он не теряется и не загружается автоматически. Он отправляется на ручную проверку. |
| Регламентное задание 1С | По расписанию опрашивает PostgreSQL на пакеты для загрузки. | Это автоматический «диспетчер» внутри 1С. Он регулярно проверяет базу и забирает только пакеты со статусом `Ready`, без участия оператора. |
| 1С:ERP | Создаёт документы учёта по данным готовых пакетов. | Когда регламентное задание находит пакет `Ready`, 1С автоматически создаёт документ по `result_json`. Оператор не выбирает пакеты вручную. |
| Integration service 1С | Возвращает результат обработки обратно в систему. | После автозагрузки документа этот слой записывает в PostgreSQL итог: пакет успешно загружен (`Imported`) или завершился ошибкой (`Error`). |
| Monitoring / Alerts | Следят за зависшими, ошибочными и долгими пакетами. | Это инструмент контроля для поддержки и ИТ. Он помогает быстро заметить проблемы, пока они не повлияли на бизнес. В мониторинг уходят статусы и технические метрики, а не содержимое документов. |
| Audit trail | Хранит историю, кто и что сделал с пакетом. | Это журнал событий. Он нужен для контроля, расследования ошибок и прозрачности процесса. |

## Главная бизнес-логика prod-варианта

1. MAX принимает документы от сотрудника.
2. Сервис создаёт пакет и передаёт его в оркестратор.
3. Оркестратор проводит пакет через on-prem OCR, on-prem LLM, проверку качества и выбор сценария.
4. Регламентное задание 1С по расписанию опрашивает PostgreSQL и забирает пакеты со статусом `Ready`.
5. 1С автоматически создаёт документ и возвращает в систему итог: `Imported` или `Error`.
6. Если качество распознавания недостаточное, пакет может уйти в `Manual review` (без автозагрузки).

## Правило безопасности

После приёма пакета в контур компании **данные документов не передаются наружу**:

- фото, OCR-текст и `result_json` остаются во внутреннем хранилище и PostgreSQL;
- распознавание и структурирование выполняются on-prem OCR и on-prem LLM внутри контура, без внешних облачных API;
- в MAX содержимое документа не отправляется обратно;
- в мониторинг уходят только статусы и технические метрики, без содержимого документа.

MAX используется только как входной канал сотрудника. Это отличие от MVP, где для пилота допустимы внешние Yandex Vision OCR и YandexGPT.

## Что это даёт бизнесу

- Понятный и контролируемый путь документа от сотрудника до 1С без ручного выбора пакетов.
- Меньше ручных потерь и зависших пакетов за счёт регламентного опроса PostgreSQL.
- Прозрачные статусы для поддержки и контроля процесса.
- Данные документов остаются внутри компании.
- Возможность масштабировать решение без полной переделки архитектуры.
