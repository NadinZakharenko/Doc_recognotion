# Архитектурная схема взаимодействия MAX с 1С через промежуточное хранилище

Ниже — целевая архитектурная схема: MAX не интегрируется с 1С напрямую, а работает через промежуточное хранилище и сервис обработки. Такой вариант хорошо разделяет канал общения, файловое хранение, OCR/парсинг и бизнес-логику 1С, а webhook в MAX штатно поддерживается через подписки с `secret` в заголовке `X-Max-Bot-Api-Secret`. [^1][^2]

## Схема взаимодействия

```text
┌────────────────────┐
│ Пользователь       │
│ MAX client         │
└─────────┬──────────┘
          │ 1. Фото документа
          ▼
┌────────────────────┐
│ MAX platform       │
│ Bot API / Webhook  │
└─────────┬──────────┘
          │ 2. message_created + attachment
          ▼
┌──────────────────────────────────────┐
│ Интеграционный сервис бота           │
│ - webhook endpoint                   │
│ - валидация secret                   │
│ - сборка пакета документа            │
│ - журнал статусов                    │
└───────┬───────────────────────┬──────┘
        │                       │
        │ 3a. сохранить фото    │ 3b. записать метаданные пакета
        ▼                       ▼
┌───────────────────┐      ┌──────────────────────┐
│ Промежуточное     │      │ Реестр пакетов       │
│ хранилище файлов  │      │ PostgreSQL           │
│ Nextcloud/WebDAV  │      │ status, user, org,   │
│ / S3 / SMB        │      │ warehouse, confidence│
└─────────┬─────────┘      └──────────┬───────────┘
          │                           │
          │ 4. событие/очередь        │
          └──────────────┬────────────┘
                         ▼
┌──────────────────────────────────────┐
│ Сервис распознавания                 │
│ - OCR / table extraction             │
│ - проверка качества фото             │
│ - поиск дублей/двух документов       │
│ - JSON результата                    │
└─────────┬────────────────────────────┘
          │ 5. сохранить JSON/статус
          ▼
┌──────────────────────────────────────┐
│ Промежуточное хранилище + реестр     │
│ - images/                            │
│ - result.json                        │
│ - preview.xlsx (опционально)         │
│ - processing status                  │
└─────────┬────────────────────────────┘
          │ 6. запрос из 1С
          ▼
┌──────────────────────────────────────┐
│ 1С:ERP                               │
│ - список доступных пакетов           │
│ - отбор по пользователю/складу       │
│ - сопоставление НСИ                  │
│ - создание черновика ПТиУ            │
└─────────┬────────────────────────────┘
          │ 7. статус/ссылка назад
          ▼
┌──────────────────────────────────────┐
│ Интеграционный сервис                │
│ - пометить “Загружен в 1С”           │
│ - отправить уведомление в MAX        │
└──────────────────────────────────────┘
```

MAX доставляет события боту через webhook-подписку, а проверка секрета должна делаться на вашей стороне в обработчике. [^1] Для вложений и медиа MAX Bot API поддерживает штатную работу с файлами, что подходит для фотографий накладных. [^3]

## Роли узлов

| Узел | Роль |
| :-- | :-- |
| MAX Bot | Принимает фото, команды, callback-кнопки, уведомляет пользователя о статусе. [^3][^1] |
| Интеграционный сервис | Центральная оркестрация: принимает webhook, валидирует `X-Max-Bot-Api-Secret`, создаёт пакет, пишет метаданные, запускает обработку. [^1][^2] |
| Промежуточное хранилище | Держит исходные фото и результаты обработки; для Nextcloud штатный интерфейс загрузки — WebDAV. [^4][^5] |
| Реестр пакетов | Хранит пакет как бизнес-сущность: кто отправил, когда, по какой площадке/складу, в каком статусе, какой результат готов. |
| OCR/Table service | Извлекает табличную структуру и реквизиты, рассчитывает уверенность, отмечает проблемы. |
| 1С:ERP | Забирает только готовые и доступные пакеты, делает сопоставление с поставщиком/номенклатурой и создаёт черновик ПТиУ. [^6] |

## Поток по шагам

1. Пользователь отправляет одну или несколько фотографий в бот MAX. [^3]
2. MAX вызывает ваш webhook и передаёт событие о сообщении; секрет приходит в заголовке `X-Max-Bot-Api-Secret`. [^1]
3. Интеграционный сервис создаёт или дополняет пакет документа, сохраняет фото в хранилище и метаданные в реестре. [^4][^5]
4. После команды “Завершить пакет” или по таймауту сервис ставит пакет в очередь распознавания.
5. OCR-сервис читает изображения из хранилища, строит `result.json`, при необходимости формирует preview-файл и возвращает статус “Готов к загрузке”.
6. 1С по своей команде получает список пакетов, фильтрует их по пользователю, площадке, складу и правам, затем забирает конкретный результат. [^6]
7. 1С создаёт непроведённый ПТиУ, а интеграционный сервис обновляет статус пакета и отправляет уведомление в MAX. [^6]

## Ключевые интерфейсы

Минимально нужны 4 интерфейса:

- **MAX → Bot service**: webhook `message_created`, callback events, attachments. [^1][^3]
- **Bot service → Storage**: загрузка файлов в Nextcloud через WebDAV `PUT` или в S3/SMB через внутренний адаптер. [^4][^5]
- **Bot service ↔ OCR service**: внутренняя REST/queue-интеграция, например `POST /recognize/{packetId}`.
- **1С ↔ Integration service**:
    - `GET /packets?user=...&warehouse=...&status=ready`
    - `GET /packets/{id}/result`
    - `POST /packets/{id}/imported`
    - `POST /packets/{id}/closed`


## Практические принципы

Лучше держать хранилище и реестр раздельно: файлы — в Nextcloud/S3/SMB, статусы и бизнес-атрибуты — в PostgreSQL. Это упростит выборки для 1С, идемпотентность и контроль дублей, а Nextcloud/WebDAV можно оставить именно как файловый слой, не превращая его в журнал процессов. [^4][^5][^6]

Для 1С оптимальнее не читать папки напрямую, а работать только через интеграционный API поверх реестра пакетов. Так вы сохраните контроль доступа, версионирование контракта и сможете заменить хранилище или OCR-модель без переработки логики в 1С. [^6]

## Рекомендуемый вариант для MVP

Для MVP я бы зафиксировал такой состав:

- MAX bot webhook service;
- PostgreSQL как реестр пакетов;
- Nextcloud как файловое хранилище через WebDAV;
- локальный OCR/table parser;
- HTTP API для 1С. [^1][^4][^6]

Если хотите, следующим сообщением я нарисую эту же схему уже в виде:

- PlantUML-диаграммы;
- Mermaid-диаграммы;
- таблицы “компонент → интерфейс → данные → ответственность” для концепт-дизайна.
